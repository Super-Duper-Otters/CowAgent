# 投资业务后续优化目标

## 背景

当前基础链路已实现公众号被动回复、技术分析缓存、利率/转债生效内容返回、缓存文件校验、并发保护和基础鉴权。后续优化目标是在不破坏现有链路的前提下，提高复用率、可观测性、返回速度和鉴权一致性。

## 1. 技术分析结果共享缓存

### 目标

技术分析结果不应只作为某个用户的待取结果保存在内存里，而应作为可被多用户复用的业务缓存。

### 期望行为

- 用户 1 请求 `A 技术分析` 并生成成功后，只要交易日数据没有更新，该结果应被固定存储。
- 即使用户 1 没有回复 `1` 取图，用户 2 请求同一个标的、同一个行情日期、同一版本的技术分析时，也应直接复用这份结果。
- 用户侧的 `1/0` 只代表“该 openid 是否有待取结果”，不应决定业务结果是否可被其他用户复用。
- 共享缓存应以 `cache_key` 为核心，至少包含：
  - 服务类型：技术分析
  - 标的标准代码
  - 行情日期
  - 技术分析 Skill 版本
  - 渲染器版本
  - 模板版本

### 设计要点

- 业务结果存储与用户待取状态分离：
  - 业务缓存：长期/按日期存储，可跨用户复用。
  - 用户待取队列：短 TTL，只保存某个 openid 当前待返回的图片顺序。
- 技术分析生成成功后，应先写业务缓存，再为当前用户建立待取队列。
- 后续用户命中业务缓存时，只需要为该用户建立待取队列，不需要重复运行 Skill。
- 如微信 `media_id` 可复用，应按图片文件 hash、mtime 和过期时间建立素材缓存，减少重复上传。

## 2. 每日内容按日期存储并可后台查看

### 目标

技术分析、利率、转债都应按日期存储，并能在后台查看、检索和取得历史结果。

### 期望行为

- 利率内容按生效日期存储。
- 转债内容按生效日期存储。
- 技术分析按行情日期和标的存储。
- 后台可以查看：
  - 日期
  - 服务类型
  - 标的
  - 生成状态
  - 缓存命中情况
  - 输出文件
  - 失败原因
  - 版本信息
- 后台可以取得历史输出文件，用于复查或手动发送。

### 设计要点

- 技术分析历史结果应复用当前 `investment_cache_entries` 和 `investment_request_records` 的关系，但需要在后台形成面向业务的查询视图。
- 利率/转债当前以 `investment_daily_contents` 为主，应保持按 `effective_date` 查询。
- 后台展示应按“日期 + 服务类型”组织，技术分析再按标的聚合。
- 文件缺失时应展示失效状态，避免后台显示可用但实际无法返回。

## 3. 最新交易日判断机制

### 目标

提高技术分析缓存命中率，避免在交易日数据未更新时错误生成新缓存；同时避免把自然日误当行情日期。

### 初步规则

- 技术分析基于最近一个已完成并可获得数据的 A 股交易日。
- 当前日期不能直接作为行情日期，必须结合数据源或交易日规则确认。
- 如果数据源明确返回行情日期，以数据源为准。
- 如果数据源不可用，不能复用不确定日期的旧缓存，应走完整生成或返回明确失败。

### 时间判断设计

可按 A 股交易时间建立“候选行情日期”：

- 交易日开盘前：最新行情日期通常是上一个交易日。
- 交易日盘中：如果系统只使用收盘后完整日线数据，则最新行情日期仍应是上一个交易日。
- 交易日收盘后：需要判断数据源是否已更新当日数据；只有数据源确认后才使用当日作为行情日期。
- 非交易日：最新行情日期应回退到上一个交易日。

### 节假日避让

需要引入交易日历，避免周末和法定节假日误判。

可选方案：

- 使用 Tushare 交易日历作为主来源。
- 本地缓存交易日历，按月或按年刷新。
- 数据源不可用时，只能使用已缓存交易日历；没有可靠交易日历时不推断新行情日期。

### 设计原则

- 数据源确认优先于时间推断。
- 时间推断只用于减少不必要查询和提高缓存命中，不应作为最终行情日期事实来源。
- 所有行情日期判断应可审计，后台记录应显示 `market_date` 和来源。

## 4. 鉴权优化

### 目标

用户输入任何消息都应先鉴权，再进入格式解析、待取结果、缓存命中或业务执行，保证提示一致且减少无效计算。

### 期望行为

- openid 不存在、用户停用、授权过期时，任何输入都直接返回权限提示。
- 账号级鉴权通过后，再解析用户输入。
- 解析出具体服务后，再做服务级鉴权。
- 待取结果回复 `1/0` 也要先通过账号级鉴权。
- 用户回复 `1` 取技术分析结果时，应按待取结果中的 `service_type` 校验服务权限，不应依赖标题反推。

### 效率要求

- 账号级鉴权应轻量，可对用户权限做短 TTL 缓存。
- 权限缓存要能在后台停用、修改服务权限后快速失效。
- 鉴权失败不得触发：
  - 股票解析
  - 行情日期解析
  - 缓存查询
  - Skill 运行
  - 微信素材上传

## 5. 返回速度优化

### 目标

在公众号被动回复限制内，尽量让用户快速得到明确反馈或图片。

### 优先方向

- 利率/转债：
  - 生效图片存在时直接返回图片。
  - 图片丢失时立即返回“今日内容尚未更新，请稍后再试。”。
- 技术分析：
  - 缓存命中时快速建立用户待取结果。
  - 未命中时立即返回运行提示，不阻塞微信 POST。
  - 生成完成后，用户回复 `1` 分次取图。
- 微信素材：
  - 增加 `media_id` 缓存，避免同一图片重复上传。
  - 记录素材过期时间，过期后自动重新上传。

## 6. 后台可观测性

### 目标

后台能解释每一次用户体验问题，包括为什么没有返回图片、为什么没有命中缓存、为什么权限失败。

### 应展示的信息

- 用户输入
- openid
- 用户状态和服务权限
- 服务类型
- 状态
- 错误码
- 用户提示
- 失败原因
- 输出文件
- 微信素材上传错误
- cache_key
- cache_hit
- market_date
- 技术分析/渲染器/模板版本

## 暂不纳入本轮的增强项

- 缓存物理删除
- 缓存统计大盘
- 预生成调度
- Redis 分布式锁
- 对象存储迁移
- 文件巡检后台按钮
